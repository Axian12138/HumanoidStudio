# RSI 数据划分与长期执行协议

你负责在 RoboSimStudio harness 上进行长期、可恢复、可审计的 motion real2sim 知识进化。输入是已经准备好的 whole body HOI 数据集，包含场景、human motion、与之配对的 humanoid motion，可能还有物体轨迹。源机器人可以是 G1 或有可用 URDF 的其他机器人，验证目标始终是 Unitree G1。涉及跨机器人时必须同时阅读 [跨机器人学习与 G1 验证](cross-embodiment.md)。你的目标是从训练样本中学会可迁移的动作重建方法，并用独立样本检验这些方法是否有用。不要把完成速度、知识条数或与 GT 数组完全一致当作目标。

本任务不包含数据下载和服务器部署。不要因为调用 skill 就重新下载数据或重建环境。先检查输入和已有部署，再开始实验。以下流程需要长期持续执行，允许慢速迭代、保留不确定结论和等待足够证据。

## 第一阶段 验证样本并划分数据

### 先定义独立样本

一个样本是一段完整、连续、可解释的交互动作，不以帧为单位随机切分。将同一录制、重叠窗口、镜像、重复导出、不同机器人 retarget 版本和近重复片段归为同一 `source_group_id`。缺少录制 ID 时，用配对关系、内容哈希及轨迹相似性补充分组，并记录不确定性。

同一组不得跨 bad、test、train。默认每组选择一个完整的非镜像代表动作参与本轮正式计数，其余变体作为同组附属材料，不增加样本数。报告组数、代表动作数、时长和动作类别分布，避免用很多相邻切片伪造样本量。

验证每个样本是否有配对场景、human 和源机器人 GT，是否能在统一时钟、尺度和坐标系下回放。有物体轨迹时检查身份、网格、时间戳和姿态对应。文件损坏、无法配对或时空约定不明的样本进入 `invalid`；证据不足以判定接触质量的进入 `uncertain`。这两类都不是 bad，暂不参与比例。

### 按机器人的 HOI 可信度分层

先在正式划分外的少量校准样本上确定质量规则，然后冻结。若无额外校准样本，则从候选池保留少量样本用于规则校准，不将其作为未来 test。质量审查可以读取源机器人模型和 GT，但这是数据整理阶段，不能据此学习 solver 修复规则；逐样本测试细节不提供给后续 train 学习过程。

评价机器人与物体、环境和地面的实际交互，至少检查：

- 接触对象、肢体、部位和动作意图是否正确；推、抓、勾、撑、搬、放、踢是否被混淆。
- 接近、接触、持续受力或持有、释放的顺序是否合理，是否存在无接触驱动、明显悬空或接触中断。
- 手、脚、膝盖、前臂与几何表面的距离、穿透、滑移和相对运动是否符合该接触类型。
- 全身支撑、关节限位、速度、动作连续性和可达性是否合理，是否靠大幅改姿态掩盖接触错误。
- 有物体轨迹时，其运动是否与机器人接触时序和空间关系一致。

按动作类别设置有单位的指标和阈值，结合完整动画审阅。不要给所有接触类型套同一距离阈值，也不要仅凭一张图片或平均 MPJPE 判断质量。记录每个判定的原因、证据和置信度。缺少力、质量或摩擦信息时，只能证明几何和运动学可信，不宣称已证明动力学真实。

得到真实的 `bad_pool` 和 `good_pool`。bad 必须有可复核的明显接触缺陷，不能只是“排名最低的 25%”；good 必须通过质量门槛，不能为了凑比例放入明显错误动作。

### 固定为 bad:test:train 等于 1:1:2

设合格的独立 bad 组数为 B，good 组数为 G。取 `k <= min(B, floor(G / 3))`，选 k 个 bad 和 3k 个 good 代表动作，形成正式样本池。选择兼顾交互类型、物体类别和动作时长；其他合格样本留在 reserve，不能偷偷用于训练或评估。

在 3k 个 good 中，以固定种子做可复现的分组随机划分，可按交互类别分层：k 个 test、2k 个 train。若约定更强的 actor 或场景隔离，须在划分算法中一并约束；约束冲突时宁可缩小 k 或暂缓冻结，不拆同源组。

最终正式代表动作数严格满足：

```text
bad = k
 test = k
train = 2k
bad : good = 1 : 3
bad : test : train = 1 : 1 : 2
```

如果没有足够的真实 bad 或 good，报告缺口并保留未完成状态。不要制造坏数据、重标标签、重复采样或切碎片段来满足比例。

冻结 `quality_labels`、`split_manifest`、随机种子、组映射和哈希。以后不因实验表现重新洗牌。bad 仅作为隔离的质量审计集合，不用于本轮知识学习、调参或晋升判断。正式比例按独立代表动作计数，同时报告时长比例，不声称时长也满足 1:1:2。

## 第二阶段 建立可比较的重建与评估协议

G1 生成器的输入是 GT 场景、human motion、任务描述和预先声明的非机器人观测。源模型只用于数据整理与 train 源动作分析/复现；test 的生成、回放和评分程序均不得加载源机器人模型。源 test GT 的语义参考由冻结的特征提取器提前生成并隔离保存，流程见跨机器人引用。若物体轨迹可用，事先决定它作为输入约束还是只作评估；所有 baseline、train、test 使用同一约定。不能给新方法额外的信息优势。

源机器人 GT 和交互参考存在单独的 evaluator 输入中。跨机器人时 train 可以在源模型上重建动作并对照源 GT，学习后还需在 train 的 G1 重建中检查可迁移性；G1 与源模型关节数组不能直接作差。先运行生成器得到候选并记录其哈希，再揭示训练 GT 误差进行诊断。train 允许反复基于误差改进知识与算法，但不能复制 GT 关节数组、逐帧查表或按样本 ID 检索答案来冒充 human 到 robot 的重建方法。

测试生成器不能读取 test 的源机器人 GT、预提取交互答案、可选 G1 GT 或逐样本历史评估报告。通过单独进程、受限输入清单或只读挂载实现隔离；评估器随后读取对应参考：跨机器人读取预计算交互描述，同模型且有匹配 G1 GT 时才读取 G1 GT。不能只依赖“同一上下文看过答案但承诺不用”。

冻结以下评价维度，并保留各项结果，不能只报一个综合分数：

| 维度 | 检查内容 |
| --- | --- |
| 同模型 GT 相似度 | 仅有匹配 G1 GT 时评价关节、身体、根部与速度误差；跨模型关节/世界手坐标误差不作为目标 |
| 跨机器人语义 | 比较接触角色、物体坐标系下的接触关系、支撑与质量转移规律、交互顺序和任务结果；同时记录量测置信度 |
| HOI 接触 | 接触部位和事件时序、接触距离与连续性、穿透、接触期相对滑移 |
| 全身质量 | 支撑、脚滑、膝或手支撑、自碰撞、关节限位、速度与加速度异常 |
| 物体关系 | 有轨迹时检查物体相对位姿、交互后位移及释放时序；无轨迹则标不可评估 |
| 实际动力学 | 仅在真实物理 rollout 中评价稳定性、物体响应和任务完成，不把 kinematic 回放计入 |
| 资源与失败 | 运行时间、求解次数、失败率以及超时与缺失输出，不能只汇报成功样本 |

坐标变换、重采样和时间对齐只能依据输入契约确定；不能逐样本拟合机器人 GT 后再报告低误差。展示原始时序与误差；任何额外对齐指标只能作为补充。

阈值、综合分数的权重、实际改善的最小幅度和允许回归范围，只能在 train 或专门校准材料上制定，在读取正式 test 结果前冻结。对于多解动作，同时检查任务和接触；不要只因某个合理姿态与 GT 不完全相同就判错。

先保存固定的基础 harness 加原只读知识库的 baseline，并保证后续比较使用相同输入、随机种子和运行预算。共享代码的变更先放实验分支及显式启用配置，保留可恢复的原版本；不得直接破坏既有工具和样例。

## 第三阶段 只在 train 上学习知识

每次从 train 选一个动作或一类重复失败机制，执行下面的闭环：

1. 根据 human、场景和任务语义检索原知识库与当前可用的 RSI 知识，记录选用和未选用的知识 ID、版本及理由。适用性判断必须在查看当前候选 GT 误差之前完成。
2. 从 human 重建 body prior，再生成 HOI motion。可以先在源机器人模型上对照源 GT，再在 G1 上实现所学规则。每次运行分别固定其模型、场景、时钟和其他约束，保存候选；不能把源模型的成功当作 G1 验证通过。
3. 同模型源重建使用 train 源 GT；G1 迁移使用跨机器人语义和 G1 自身约束，有匹配 G1 GT 时再附直接误差。用对应冻结指标诊断差异，结合完整动画分析错误机制。区分数据问题、适用条件错误、算法错误和物理验证缺失。
4. 提出可迁移的文字规则或修复方法。明确适用条件、失败边界、必须从当前输入重新测量的量，禁止把某一 take 的坐标或帧号包装成普遍知识。
5. 在多个 train 样本上比较使用前后，保留反例和失败尝试；只有一次成功时标记证据有限。实现应复用既有工具，成熟的共用算子放在 `robosimstudio/humanoid_real2sim/`，实验入口放在 `scripts/humanoid-real2sim/`。
6. 将有直接证据的候选写入 `examples/rsi-learned/`，赋予稳定 ID 和不可变版本。正文为主要产物，附最小 motion/审查材料及全量 outputs 链接。
7. 对候选在 train 上做复现和消融检查，通过后冻结“知识正文＋实现代码＋检索/选择策略＋跨机器人特征与角色映射＋参数＋评估协议”的完整版本，提交到测试队列。

新知识的起因、内容、阈值、适用条件和算法修改必须能追溯到 train 证据。不得用 test 的失败动作、数值、截图或轨迹来补充一条新规则。

## 第四阶段 test 只判断知识是否有用

test 在这里是知识筛选集。它允许决定保留、拒绝、晋升或删除知识，不允许生成、修订、调参或重新训练知识。

对每个冻结版本：

1. agent 只依据测试样本的场景、human 和允许的观测，自主判断要不要使用该知识。保存决策；不得看 GT 或试跑结果后再挑有利的知识。
2. 只使用冻结的 G1 模型和 harness 完成一次测试重建，不在 test 失败之后反复修动作。与不包含该候选知识的版本做配对比较，保持其他知识、代码、种子和预算一致。
3. 同时报告“知识被选用时是否有效”和“包括未选用及失败样本在内的整体策略效果”。必要时做单条消融，避免把多条知识或代码改动的收益全部归给一条规则。
4. 使用事先确定的接触质量硬门槛、改善幅度与回归限制判定。足够多的独立样本上有稳定改善且没有不可接受回归，才可晋升；样本少、证据冲突或只改善相似度却破坏接触，标记不确定或拒绝。
5. 晋升时把冻结版本原样复制到 `examples/rsi-validated/`，只增加验证状态、适用范围的原始声明和评估证据链接，不根据 test 重新编写规则。每个 train 候选版本与验证副本共享内容哈希。
6. test 的详细报告保存在 evaluator 的隔离输出中；学习流程只接收晋升、保留待定、拒绝或撤销等状态及审计 ID。不得把失败原因自动写回 train 的提示词、超参数或新知识正文。

提前划分 test 的消费批次并记录查询次数，尽量让新候选面对尚未使用的独立测试组。用完测试预算后可以继续 train 学习，但停止新的验证晋升，直到有新的独立测试数据。不得换种子重洗 test 或把它改为 train。

同一个 test 被反复用于知识筛选会形成选择偏差，因此结果只代表“在该筛选协议下验证有用”，不能宣传为无偏最终泛化性能。若未来需要最终泛化评估，应额外使用独立、未参与选择的封存数据；不改变当前 1:1:2 的定义。

## 第五阶段 文字优先的知识管理

两个新目录分别维护自己的 `README.md`、`index.json`、证据清单和结果清单，不复用或修改原库的索引。按可复用动作与失败机制组织正文，不能把所有运行按任务名堆成知识。

每条知识至少用完整语言说明：

- 人、机器人、物体和支撑面正在发生什么，以及知识解决的问题。
- 可执行的方法、适用条件、不适用条件、需要重新测量的量。
- 训练反例、机制解释、修复前后行为；没有确认的因果时明确写假设。
- 支持结论的独立 train 样本和反例，以及未验证的范围。
- 源机器人与手模型、可迁移交互原则、源模型专属参数、G1 适配方法和证据；实现代码版本、复现入口、所依赖的其他知识版本。
- 状态、候选版本、验证状态和证据链接。

GT、result 和 artifact 是支撑正文的证据，不能取代解释。GT 是数据集参考，result 是该方法实际生成并通过所声明检查的结果，两者必须区分。优先引用只读 GT 清单和哈希；有必要且允许保存时才精选少量 GT。完整数据和测试细节留在 outputs，不放入检索可读的知识正文。

已确认结果放各自知识库的 `results/`；失败、对照和待审材料放 `artifacts/`。所有精选文件记录来源、SHA-256、时间窗和能证明的结论。没有实际成功结果时不制造 `result_ids`；验证了运动学不等于验证了抓取动力学。

生命周期为：`draft → train_supported → frozen_for_test → validated`，另有 `inconclusive`、`rejected` 和 `retired`。修改知识正文、算法或依赖即创建新版本，旧版 test 通过状态不能自动继承。

当证据表明知识基本错误时，从 `rsi-learned` 和 `rsi-validated` 的当前可用正文、索引及检索缓存中删除对应版本，撤销引用它的组合知识的验证状态。只在 outputs 审计日志中保留删除原因、版本哈希与证据 ID；Git 历史不用重写，历史错误知识不得再次作为可用规则检索。一次测试波动或不适用不等于普遍错误，应先依据冻结标准区分不确定、适用性错误与基本错误。若需修订方法，只能从 train 重新建立证据链。

## 长期运行与每日反馈

这是长期任务，不要求立即完成。先完成小规模端到端闭环，再扩大 train 的机制覆盖；每轮可以只解决一个问题。没有可靠改进时保留“无有效新增”，不要为了每天有成果而降低门槛。

将运行分成可恢复的有限批次，保存待办队列、已完成 run ID、代码/数据/知识快照、种子、状态和下一步。设定每批资源上限，出现重复基础设施失败时暂停该批并报告，不无限重试、不启动无限增长的实验。

每天按约定时间生成并交付一份进度报告，包括：

- 今日数据审查和划分状态，新增/排除样本及原因。
- train 完成、失败、超时和仍在运行的数量；主要错误机制与量化变化。
- 新知识、晋升知识、待定知识、删除知识的 ID、版本和理由。
- test 使用量、剩余独立批次和泄漏审计结果；详细测试失败分析不回流学习流程。
- 最佳已验证版本相对固定 baseline 的变化、回归、证据范围和仍未验证的内容。
- 资源消耗、阻塞、需要用户处理的问题以及明天准备验证的假设。

完整日志按真实时间追加。每天都要反馈，即使当天无进展、任务暂停或没有新知识。agent 不能通过一句“明天继续”替代实际持续执行机制：开始长期任务时必须核实运行平台是否支持持久 worker 与每天唤醒/交付；有支持就配置并验证，没有支持就明确说明限制并提供可恢复的状态入口。仅写定时 Markdown 文件不等于用户收到了每日反馈。只向用户指定的通道交付，不自行给其他人发消息。

每天更新 `${REPO_ROOT}/outputs/humanoid-real2sim/<date>/rsi_<dataset-id>/daily_report.md` 和最近状态索引。暂停、恢复或更换执行 agent 时，交接未完成 run、剩余测试预算、当前可用知识版本和最后验证证据，避免重复消费 test。

## 验收与停止条件

第一轮完成至少需要：真实质量分层和可复现的 1:1:2 清单；只读场景/GT 与隔离的测试评估入口；固定 baseline；一次 train 学习、冻结、test 判断、知识晋升或拒绝的闭环；原知识库未受污染；每日反馈确实可交付。

后续不以“知识足够多”或“没有报错”宣布成功。逐轮报告接触质量是否改善、不同动作类别是否迁移、是否引入回归及证据是否充分。用户要求暂停或停止、输入前提不成立、测试预算耗尽或资源配额不足时，停止相应依赖工作，保留可恢复状态并如实报告。

调用本 skill 后先完成启动审计和实验配置，再按上述阶段推进。未提供实际数据集时，只报告缺少哪些启动输入，不自行替换数据集或生成假 GT。
